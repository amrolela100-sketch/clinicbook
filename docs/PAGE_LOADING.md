# Page loading and development isolation — audit #19

## Implemented scope

- Public, account, workspace and platform URLs now have file-based App Router
  pages. `src/app/[...path]/page.tsx` only rejects unknown routes. The existing
  server-side authentication, role and onboarding redirects are retained in
  `src/lib/clinic-routes.tsx`, as are doctor metadata and nonce-bearing JSON-LD.
- `src/lib/services/app-data-service.ts` supplies the same authorized snapshot to
  the root server layout and `/api/data`. `AppProvider` starts with that snapshot,
  so public content no longer waits for a browser `/api/data` waterfall. If the
  server load fails, the existing client fetch/error path remains available.
- The home hero is not rendered with initial zero opacity. Search initializes
  its city and specialty from the URL before hydration. Form label IDs and SVG
  title text remain stable between server rendering and client interaction.
- The small `AgentChatLauncher` renders the entry button without importing the
  chat/booking transport into the initial public-page scripts. Opening it loads
  the drawer and opens it immediately; subsequent closes/reopens retain it.
- Browser flows distinguish visible server HTML from hydrated event handlers,
  wait for real authentication/save responses, and find a genuinely bookable day
  rather than assuming that tomorrow is a working day.

The root document deliberately remains **dynamic**, not SSG. It contains a
per-request CSP nonce and a potentially personalized snapshot. Production
responses retain `no-store`; introducing a shared static document would violate
those security constraints. Workspace loading has a scoped fallback; public
content does not depend on JavaScript revealing suspended fragments.

This is not a complete per-view client-module split: `public-pages.tsx` remains a
shared view module. No complete JavaScript-size, Lighthouse or representative-
volume performance claim is made.

## Reproduced development failures and mitigation

Three independent problems were observed:

1. Each development browser run added a UUID-specific type directory to the
   tracked `tsconfig.json`. Next's installed TypeScript setup explicitly adds its
   selected `distDir` to the selected TypeScript config.
2. Webpack development intermittently returned **HTTP 500** on the first
   compilation of `/search`, with
   `TypeError: __webpack_modules__[moduleId] is not a function`. Later requests
   in the same run could pass. Isolating the TypeScript config fixed its mutation
   but did **not** eliminate this separate Webpack failure.
3. With Next's default legacy browser targets, Turbopack lowered logical CSS
   insets into physical left/right rules selected by `:lang(ar)`. An Arabic page
   with `dir="ltr"` therefore still got the RTL switch positions, despite the
   input's actual direction being LTR. The generated CSS and five repeated LTR
   failures confirmed this; changing the language or expected geometry would
   have hidden the problem.

Browser runs now have an isolated SQLite database, build directory and ignored
`tsconfig.e2e-<run-id>.json`. The test server and Node-side fixtures share the
same run ID. The test config extends the normal compiler settings; the tracked
config excludes `test-results/` and no longer accumulates generated includes.
The before/after SHA-256 check below verifies that it remains byte-for-byte
unchanged.

The same rendering cases passed **9/9** with Turbopack, and **16/16** production
tests passed using the unchanged `next build` / `next start` path, including
home → search → doctor navigation without JavaScript. Development and demo E2E
therefore use Turbopack by default. Webpack remains selectable for diagnosis;
this is a development-bundler workaround, **not an upstream Webpack repair**.
Retries and longer assertion timeouts were not used to hide the HTTP 500.

The package now declares browser targets matching the installed Tailwind 4
baseline: Chrome/Edge **111+**, Firefox **128+**, Safari/iOS Safari **16.4+**.
The [official Tailwind compatibility guide](https://tailwindcss.com/docs/compatibility)
documents the Chrome 111, Safari 16.4 and Firefox 128 requirements. This prevents
legacy language-based lowering and preserves native logical insets. The
unchanged off/on/off geometry checks then passed **10/10** across RTL and LTR;
the tests also assert the actual CSS direction. These targets are a support
baseline, not a claim of exhaustive cross-browser testing.

`next-env.d.ts` is still generated by Next for the currently selected build
directory. A normal production build restores its standard `.next/types/`
reference; do not commit an individual test-run reference from that generated
file.

## Reproduction and verification

```powershell
npm run dev
# Optional Webpack development comparison:
npm run dev:webpack
```

For the browser comparison, set `CLINICBOOK_E2E_BUNDLER=webpack` before the
rendering test; restore the previous environment value afterwards. The default
is `turbopack`. Production tests do not use this setting.

```powershell
$before = (Get-FileHash -Algorithm SHA256 -LiteralPath 'tsconfig.json').Hash
npm run test:e2e
if ($LASTEXITCODE -ne 0) { throw 'Browser regression failed.' }
if ((Get-FileHash -Algorithm SHA256 -LiteralPath 'tsconfig.json').Hash -ne $before) {
  throw 'The browser run modified the tracked TypeScript configuration.'
}

npx playwright test tests/e2e/rendering.spec.ts --repeat-each=3
npx playwright test tests/e2e/ui-accessibility.spec.ts -g "availability switch" --repeat-each=5
npm run test:unit
npm run test:production
npx tsc --noEmit --incremental false
```

The no-JavaScript tests check actual successful HTTP responses, readable home
content, URL-selected search results and server authorization. Production also
checks readable doctor content/metadata, non-cached documents, no initial
browser `/api/data` request, lazy assistant script delivery and CSP hydration.
Fixtures are synthetic, with Supabase and Redis protocol endpoints on loopback;
they do not exercise real GoTrue, Realtime, Upstash or patient data.

## Release boundary

This closes the local initial-rendering, assistant-loading and development-
isolation work. It is **not a production sign-off**, full WCAG certification or
proof that every development hot-reload condition is safe. No workflow file,
remote database migration or deployment was changed in this step.

Lint/coverage gates, migration upgrade/retry testing, historical documentation
corrections, final release evidence and live staging checks remain separate
audit work. See `PRODUCTION_HARDENING.md` for the wider deployment constraints.
